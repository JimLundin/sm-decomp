# Improve measured throughput

Read [PLAN](../../../docs/PLAN.md) first, then [REVIEW](../../../docs/REVIEW.md)'s
Milestone plan at each item's start. Direct user instructions win. REVIEW sets
priorities; PLAN owns required checks, resources, Git and completion.

Keep ready core implementation/build/replay and publication supplied ahead of
optional audits and reports. Use an explicit purpose, bounded result and root-owned
allowance; preserve current source owners, live jobs, frozen inputs and accepted proofs.

1. Measure the source/review/build/capture/replay/publication bottleneck on current
   work. Carry original handles and exact input/artifact identities rather than
   repeating successful campaigns to collect another timing.
2. Make one bounded correction or experiment on that necessary work. Use current
   user host/cache authorization and the same resource ledger. If it changes
   ownership/interfaces/backend, first read the [destination](../../../docs/target-architecture/README.md)
   and its Windows policy; reach only the relevant technical contracts.
3. Compare useful throughput and resource costs using comparable toolchain/profile,
   inputs, workload and boundaries. Claim speedup only from actual comparable
   evidence; report unchanged/negative outcomes and unmeasured boundaries honestly.
4. Record actual phase/launch START, READY and terminal EXIT when available.
   Keep queue, metadata, handoff, collection and ref-observation times distinct;
   report unknown boundaries and elapsed/idle durations rather than inventing them.
5. Send the minimal result and next action before extended prose. Repeat checks
   only for changed dependencies or a new concern. Preserve source/ROM/native/input/
   codec/loader guards and all acceptance attribution.

Count verification/support work separately from engine changes. Process improvement
or executor completion does not establish architectural/size/project completion.
